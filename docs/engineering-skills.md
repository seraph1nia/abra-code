# Worker engineering guidance

Five portable, offline procedures improve the work inside existing controller checkpoints. New coding admissions require role-relevant skills to be available; workers load a procedure through the native `skill` tool only when its trigger applies. A small edit does not require five investigations. Availability and native loading are separate from behavioral proof; context diagnostics retain `loading: unobserved`.

| Native ID              | Trigger                                           | Explore                                         | Apply                                                                        | Review                                                                |
| ---------------------- | ------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `abra-codebase-design` | Caller interface, ownership or test seam decision | Plan in assigned change                         | Implement accepted design                                                    | Assess read-only                                                      |
| `abra-domain-modeling` | Ambiguous domain vocabulary                       | Propose terms and documentation tasks in change | Update vocabulary/ADRs only in accepted scope                                | Read existing vocabulary                                              |
| `abra-diagnosing-bugs` | Difficult in-scope failure                        | Plan relevant reproduction                      | Bounded red-capable reproduction, predictions, fix and original-case recheck | Assess available proof                                                |
| `abra-verification`    | Observable behavior                               | Plan acceptance proof                           | Execute relevant local recipe/check                                          | Assess current content, matching receipts and accessible observations |
| `abra-blast-radius`    | Concrete downstream/persisted safety assumption   | Plan relevant acceptance                        | Exercise actual consumer/decoder/runtime path                                | Assess proof and explicitly unproven cases                            |

Explore full-spec prerequisites are design, domain modeling and verification. Apply full-spec/lightweight prerequisites are all five. Review full-spec/lightweight prerequisites are design, verification and blast radius. Research-only retains its existing prerequisites. `abra-openspec-execution` remains a full-spec prerequisite and user-configured requirements remain additive. One shared selection in `src/opencode/engineering-skills.ts` drives both capability defaults and generated conditional pointers.

Explore writes only its assigned planning artifacts. Apply cannot redefine accepted scope; a contradiction is an existing worker question with both sources and a stop on dependent work. Review remains read-only, with shell limited to the existing browser exception. Central Abra can discover the skills but hands development work to the assigned worker. There is no extra approval, report endpoint, skill-completion gate, delegation, model-routing or delivery procedure. Existing checks, finite correction budgets and independent Review retain authority.

Review includes staged, unstaged and untracked implementation/proof in the current verified worktree. Source inspection, a matching controller command receipt and an accessible observed outcome are different forms of evidence. Apply progress output and scratch paths are not automatically durable or available to Review. Applicable missing full-spec proof is `not_verified` under the existing dimensions; lightweight Review uses the short contract. A skill invocation cannot clear either contract.

Use a foreign repository's instructions, local recipe or documented verification commands. Missing recipes do not authorize generating a skill, installing packages or creating a glossary. Report an unavailable runtime prerequisite through existing questions/waits. Recipe authoring requires accepted scope. AbraCode's own [verification recipe](verification/README.md) is repository documentation, not an extra portable skill. Changes to mapped journeys must update the relevant map entry in the same scoped work. Evidence must survive fixture cleanup; cleanup targets only verification-created resources, never controller-owned sessions/worktrees.

Retained prompts validate exactly their captured skill/tool groups and provenance without acquiring new defaults, including captured but not yet submitted prompts. Actual request-time tool enforcement and current permission-policy compatibility remain mandatory. Captured context identities, guidance and digests are not rewritten by an upgrade. A deliberate fresh prompt obtains current defaults. Rollback removes pointers/defaults before bundled assets; keep assets referenced by retained prompts or surface an explicit capability blocker and request a fresh authorized turn.
