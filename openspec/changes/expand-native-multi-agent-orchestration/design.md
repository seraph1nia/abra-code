# Design

## Context

See [proposal.md](proposal.md) for motivation and the eight delta specs for behavioral contracts. This audit describes the checkout observed on 2026-10-18, including pre-existing uncommitted changes. No implementation or native test was performed during proposal creation.

Correlated management-to-worker requests, explicit replies, atomic batches, task dispatch profiles, scoped leads and retained isolated HTML generation are the missing behaviors.

### Native evidence and limits

`package.json` pins CLI/plugin/client/schema/util at 2.0.28. Read `docs/supported-apis.md` before applying changes. Installed files inspected during planning:

- `@opencode/plugin/dist/effect/session.d.ts`: prompt hooks expose `sessionID`, `messageID`, mutable prompt, metadata and delivery. The plugin session domain exposes prompt/context/interrupt but not inbox/form APIs.
- `@opencode/client/dist/effect/api/api.d.ts`: `SessionPromptInput` accepts native session ID, optional message ID, text, optional attachments/metadata, delivery and resume; its output is `SessionInbox.User`. `session.inbox.list`, `.cancel({sessionID,inboxID})` and `.update({sessionID,inboxID,delivery})` are native client operations.
- Installed `@opencode/schema/dist/{session-inbox,prompt-input}.js` implements queue/steer delivery and inbox identity/payload schemas. Exact payload comparison must cover attachments, not just a trusted-looking metadata label.
- `@opencode/plugin/dist/effect/agent.d.ts` permits registry update/remove/default, not adding agents. Lead agent profiles must come from supported generated native configuration/agent files and be validated in native inventory.
- The host execution/inbox implementation is bundled in the installed CLI executable; declarations and existing documentation do not establish hook timing, duplicate-ID behavior, busy steering consumption or restart queue guarantees. Milestone 0 must inspect the matching bundled implementation/source evidence and exercise those semantics on the real pinned server before enabling follow-up admission.

The existing native test rejects direct queue/steer prompts to a worker and proves they make zero provider calls. It does not exercise successful `work_control steer`. The source mismatch is a suspicion with a concrete path, not a reproduced bug. No OpenCode upgrade is planned.

## Goals / Non-Goals

**Goals:** Trace every new instruction from controller intent through native admission to explicit business response; compose existing coordination/capacity; keep all user checkpoints in Abra; retain native-owned execution history and portable evidence; deliver focused independently verifiable slices.

**Non-Goals:** Generic transports/envelopes, a second lifecycle or scheduler, automatic scope interpretation in controller code, recursive supervisors, additional harnesses, permission upgrades for reports, central execution of repository-supplied TSX, external report services or claims of OS isolation. Firstmate is a user-experience reference only; this design relies on the requested behaviors rather than its internals.

## Decisions

### 1. Make steering a blocking native correctness milestone

Extend the deterministic loopback provider in `tests/e2e/native.test.ts`/its owned fixture helpers with a held busy worker and observable prompt markers. Call the real controller steering tool, record the actual native error/provider count, and compare queue and steer behavior. Cover valid initial assignment, authorized follow-up, forged metadata, direct queue/steer, wrong session/generation, rebound text/attachments, pause and response loss. Keep these tests in the disposable installation; never restart the user's service or write their remotes.

If native evidence confirms the guard conflict, first fix only retained follow-up prompt authorization and recovery. If it disproves the suspected path, retain the positive/refusal tests and implement the same explicit identity contract only where missing. The wider message protocol cannot begin before the positive native case and refusal cases pass. Do not skip the guard or special-case a `source` label.

Use one authorization projection: initial intent comes from the existing execution and immutable WorkerContext capture; follow-up intents come from controller-retained records. Return expected session, role, generation, delivery and exact captured prompt. Keep `e.prompt_id` and `worker_context_id` as assignment identities; replacing either for steering would invalidate provenance and completion checks. Re-read assignment/intent at native admission and provider/tool authorization boundaries. Historical sessions remain guarded even after role replacement.

For compatibility, `work_control action:steer` routes through the same intent function. Add an optional explicit request identity for external retries. For calls without it, derive stable identity from the actual native invoking tool-call identity plus execution generation; propagate this trusted context through the tool wrapper. Internal/programmatic callers must provide an identity. A second deliberate tool call is a new instruction; retrying the same admission is not.

Alternative rejected: adding another allowed message ID directly to the guard without retained payload, generation, reconciliation and ownership. It fixes a symptom while leaving a replay/rebinding gap.

### 2. Store a small communication intent beside its execution

Add `workflow/message-contracts.ts` and a cohesive `workflow/messages.ts` coordinator only because routing/correlation and explicit response are not native business concepts. Reuse branded request/message/session/execution IDs and Effect Schema. Initial implementation stores a bounded optional message collection in the existing execution record, written under existing coordination; no new database, inbox daemon or transcript mirror. Cap at 256 retained requests per execution and 8 KiB per body/reply, with bounded evidence references and an explicit limit error; never evict unresolved requests. These are engineering defaults, not a generic retention framework.

Each record needs request ID, native prompt ID, issue/execution/generation, trusted sender session, recipient role/session, kind, exact rendered prompt/body, delivery, response requirement (`none`, `acknowledgement`, `answer`), lifecycle status, timestamps and optional reply/evidence/disposition. A link to an existing decision or source finding supplies correlation when needed; do not maintain a separate free-form correlation namespace. Reusing a supplied correlation key with changed input fails. Persist rendered wrappers and provenance exactly once so restart never rebuilds changed content under an old ID.

State progression is `pending -> admission_uncertain -> admitted -> acknowledged -> answered`, with answer allowed directly from admitted and an acknowledgement-only request resolved at acknowledged. `cancelled` and `superseded` record authorized terminal dispositions. Native evidence can establish admitted; only an explicit authorized reply establishes acknowledged/answered. Required-response obligations are projections of this record, not duplicate `Decision` objects. They block the affected checkpoint until response or explicit disposition; unrelated work continues. Nonrequired messages do not indefinitely block delivery after confirmed native quiescence, but their unresolved response history remains honest.

Use existing execution operation ownership around admission/cancellation and short record coordination for intent/result commits. A worker reply must remain able to commit under short coordination while a slow native operation is in flight. Always merge into fresh records with generation/intent checks rather than overwriting concurrent replies. This avoids a callback deadlock and lost answers.

### 3. Keep delivery mechanics native and capacity aware

Before submission, persist the complete intent and reserve capacity if the eligible current role is idle. Mark the attempt uncertain before calling `runtime.prompt` so every crash window has a retained native ID. Check location identity and existing preflight/request-time capability policy. Queue/steer does not grant activation of a historical role or a completed workflow phase.

On success retain native admission. On ambiguous response, read both inbox and context by retained ID and verify recipient/payload where available. A failed read or an unexplained absent result is uncertainty, not permission to mint a new ID. Retry the same ID only when verified native semantics and fresh evidence establish safe non-admission. If 2.0.28 cannot establish this, retain uncertainty for explicit recovery rather than weaken the no-duplicate requirement. No body-text heuristic or automatic new session is permitted.

Busy workers reuse their existing reservation. Pending messages that cannot yet activate remain outside native admission until capacity is available. Admitted/uncertain instructions that can run keep the reservation. Change `WorkerSessions.observe` so session-level success/idle cannot release capacity or advance a role while its inbox can still activate it. Reconcile each retained prompt and required response against native evidence; do not attribute a later message's outcome to the original assignment. Quiescence, no applicable queued/uncertain activation and resolved required responses form the checkpoint barrier. Missing explicit replies produce an actionable obligation, never a claim that a completed worker answered.

Pause/supersession must cancel all owned queued instructions, not just `e.prompt_id`, and confirm inbox absence plus actual native stop. If consumption won the race, preserve that evidence and follow existing interrupt/stop ownership. A business disposition cannot erase executed effects. Late replies from inactive generations are refused; already persisted replies stay historical.

### 4. Add only the tools that own missing business semantics

| Tool/route                                      | Contract and ownership                                                                                                                                                                                                                                                                                                            |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `abra_work_message`                             | Explicit authorized management caller; issue, destination role/validated optional session, bounded body, stable request ID, queue/steer, optional response requirement and retained finding/decision reference. Resolve actual session in controller. Optional cancel action uses the same record and stop safeguards.            |
| `abra_worker_reply`                             | Worker-only discriminated action: acknowledge/answer an expected request, or submit a stable keyed finding with optional nominated destination. Validate native caller, current generation and immutable duplicate semantics. A nominated destination stores a forwarding proposal for Abra, never unrestricted direct prompting. |
| `abra_work_messages`                            | Read-only bounded pages (default 20, maximum 50), totals/outstanding counts, statuses and reply evidence. Scoped management can read only its authorized issues.                                                                                                                                                                  |
| Existing worker question/progress/wait/decision | Retain existing ownership. Delivering an answered question back to the worker references its one `Decision` and uses a durable prompt intent; it does not open a second question.                                                                                                                                                 |

Worker-originated findings are retained as communication evidence, notify Abra through existing attention, and can be forwarded by `work_message` with a source reference. This covers unsolicited Research-to-Apply findings without granting workers native session access. Forwarded text is clearly delimited untrusted evidence; the destination's accepted scope and role policy remain authoritative.

Update role filtering, strict input/output schemas, structured native output equivalence, guard dispatch and diagnostic eligibility together. A diagnostic management turn can inspect/reply within existing permitted obligations; generic scope-changing instruction/steering remains denied. Automatic corrections continue through finite correction policy. Do not let a lead or automated notice inherit unrestricted central `abra_*` authority.

### 5. Make batch intake one SQLite transaction

Add `createBatch` to `WorkIntake`/`WorkGraph`, exposed as `abra_work_create_batch`. Input is a stable `request_id` plus 1–32 tasks with `client_key` and the existing WorkInput fields. Keep `description`, `workflow_policy`, scope, quality and priority conventions instead of inventing a second goal schema. Dependencies are tagged local-key or existing-issue references. Resolve all repository policy/registration data before the transaction and revalidate the applicable registration identity at the controller boundary.

Canonicalize definitions by local key and dependency set. Generate all new issue IDs before inserts; within `BEGIN IMMEDIATE`, validate references and cycles over the resulting graph, insert issues/request identities, then dependency edges and events. Retain a small batch receipt table in the same database containing canonical input and key-to-issue mapping. Derive stable per-item request IDs from batch identity and key. Conflicting existing identities fail rather than adopt unrelated issues. The transaction contains no asynchronous native/storage operations and emits invalidation only after commit. Reordered identical input returns the original mapping.

The existing SQLite abstraction already supports transactions, so partial-result orchestration is unnecessary. Batch creation is separate from scheduling; after commit the existing monitor is signalled. Policy recommendation and decomposition belong to Abra's orchestration guidance, using separate tasks only for meaningful independent scope/investigation. A model recommendation never downgrades a configured gate.

### 6. Extend admission fairness rather than add a scheduler

Keep `Scheduler.tick`, `Controller.ready/start`, graph claims, role limits and retained-resource rules. Choose highest-priority eligible work first; within that priority, rotate repositories and use existing deterministic issue order within each repository. Persist one small last-admitted repository cursor per priority through existing records under coordinator leadership. Commit it only after observing the retained claim/admission intent; startup may rotate from a recovered claim but must never infer a second execution. Crash before cursor update can affect one tie-break, not ownership or eventual fairness.

Continue the current catch-and-continue behavior for independent admission failures. Dependency closure/capacity release/native completion already trigger reconciliation or are covered by its fallback interval; use the same event queue. Messages may delay role transition but do not create another scheduler lane. Return concrete capacity/dependency/authority reasons through current readiness. Default `auto_schedule:false` stays false on upgrade.

### 7. Compose supervision posture and derive status without another lifecycle

Add optional `supervision_mode` through `config/{contracts,load,presentation}.ts`. With no mode, preserve all legacy settings. With an explicit mode, reject conflicting explicitly supplied `auto_schedule` rather than silently reinterpret it: manual maps to false, attended-automatic/unattended to true. Normalize existing flags after parsing so a decoding default does not masquerade as an explicit conflict.

Manual suppresses new optional model diagnostics/repairs, while observing and completing already authorized deterministic operations/forms. Attended automatic uses the existing configured finite budgets, surfaces meaningful decisions/deliverables and permits eligible scheduling. Unattended uses the same budgets/authority but coalesces routine completion reporting and retains human-owned questions for later attention. No mode increases a budget, auto-resumes a pause, accepts a scope change or supplies an approval receipt. The resolved posture controls operation/notification policy, not per-execution permissions.

Extend the existing monitor and AttentionService. Retain deduplicated message-blocker/answer/completion notification identity; reuse native admission evidence for uncertain notification delivery. Human forms and mandatory obligations must not disappear behind spent optional diagnostic budgets. Reuse ongoing `complete-work-reliably` mandatory routing behavior once its actual implementation is reconciled; do not implement a competing route. Routine answers use the existing supervisor-owned decision API with sufficient evidence and finite diagnostic authority.

Extend the shared read model with one documented primary class: completed; unsafe recovery; human decision; supervisor decision; explicit failure (provider/check/review); delivery/CI wait; dependency wait; suspected stall; pending admission/capacity; running; otherwise observed idle/unknown. Preserve additional blockers in detail. Pending native inbox overrides an idle-looking session. Counts derive from the same projection with observation time, not editable persisted classifications. Expose via existing `work_list/status` and native RPC rather than a new dashboard.

### 8. Resolve task dispatch before capturing execution configuration

Extend normalized WorkInput/issue data with optional per-role complete model or profile selection. Profiles contain only worker role and complete existing WorkerModelSchema; they do not contain tools, permissions or natural-language rules. Permit repository per-role dispatch defaults using the same selectors. Reject same-level model/profile ambiguity and role mismatch. Resolve precedence as explicit task model, task role profile, repository model/profile, existing role override, required default. Variant belongs to the selected complete model, never another level.

Capture the resolved choices plus source in `configuration_snapshot` before provisioning and use them at every later role admission. Native location inventory remains the readiness check; missing provider/model/variant is a blocker. Existing explicit idle-worker retry/switch policy stays separate and cannot silently rewrite earlier snapshots. Changes to configuration affect new work only. Batches must include dispatch choices in their immutable input identity.

### 9. Introduce leads as scoped management principals after messaging

Retain one lead registration record keyed by branded lead ID: parent Abra session, exact repository IDs, native session intent/ID, captured selection, enabled state and registration revision. OpenCode owns conversation/persistence. Do not extend execution `Role`; a lead is a separately typed management principal. Leads run at the central managed location with narrow read-only native permissions and repository-filtered management tools.

Generate a static hidden `project-lead` native profile through existing managed configuration assets, then verify inventory before session creation. The installed registry editor cannot dynamically add a profile. Retain native session intent before create and validate native ownership metadata/location against the registration on every reconnect; metadata by itself never authorizes adoption. Scope changes, disable and re-enable advance registration revision, invalidating pending turns/replies as appropriate.

Add principal resolution to tool registration: central Abra gets existing authority; an enabled lead gets an explicit endpoint/action allowlist plus an exact repository predicate; workers keep their current path. Apply scope checks to detail reads, messages, batch proposals and routine answers, not only tool visibility. Leads can submit bounded task proposals for Abra to admit through existing intake; initial leads cannot independently start/merge/close work. This satisfies management assistance without granting new lifecycle authority. Human questions/forms always remain in Abra.

Lead native read/glob/grep tools must also be confined to explicitly allowed repository roots through native permissions and realpath-aware hooks. The central session location does not grant arbitrary reads of installation state, other projects, credential files or plugin records. If a native read tool cannot enforce that predicate, omit it from the lead and expose only bounded scoped controller evidence. Cross-project scope tests must exercise native file tools as well as management endpoints.

Reuse message records for lead instructions/notices with registration revision in place of worker generation where appropriate, using a small recipient discriminant rather than optional unrelated fields on every message. Worker-destination records remain execution-bound; lead task proposals/notices are bounded records on the lead registration and reference issues. Reuse one admission/reply implementation via a narrow validated recipient binding, with no recursively managed hierarchy. Persist intent and one authoritative source reference rather than atomically pretending to update lead and worker records. Reconcile partial notification projections from the source record.

Bound management work through existing attention capacity and configured finite diagnostic turns: one active lead turn per registration; queued/uncertain lead admissions retain the slot. Do not count a lead as an Apply/Review worker or let it bypass finite model-turn limits. Disabled leads cannot admit new turns; reconcile/cancel owned queued messages and confirm interruption before declaring a running lead stopped. Existing work/decisions remain controller-owned.

### 10. Extend the report toolkit and current report owner

Keep `templates/reporter/src/report.tsx` as the documented manual entry. Extract only components used by two actual examples: an architecture/research snapshot and a verification/review report. Begin with header/section, evidence/disclosure, code reference/diff and status/timeline primitives; use semantic HTML and existing CSS. Solid signals provide local search/navigation/views. Build-time `.mmd` compilation already supports multiple flow/sequence/state diagrams; extend tests and examples rather than shipping Mermaid runtime.

Define a small optional snapshot schema near existing report contracts: version, identity, observed time, typed evidence references and bounded sections/findings/check outcomes. No universal page DSL. Capture it read-only through controller queries; label status as a snapshot and missing fields unavailable. Render data with Solid text nodes, escaped JSON embedding and link-scheme validation; never `innerHTML` repository strings. Only SVG produced by the trusted existing Mermaid compiler uses its existing render path. Constrain generated diagram input through the existing strict compiler/security configuration and reject unsafe external resources.

An explicit authorized `work_report` generation action extends the current Reports owner with a narrowly defined build adapter; its default existing read action remains read-only and diagnostically inspectable. Generation has its own action-specific authority and is not implicitly allowed by the read action's diagnostic eligibility. It accepts validated data and trusted templates, never arbitrary repository HTML/TSX, shell commands or import paths. Read-only Research submits its normal retained report with an optional keyed visual-render request; controller processing uses the same builder without granting Research the management tool, editing or shell privileges. Manual executable TSX authoring stays in an already authorized writing worktree or an operator's checkout, following ordinary source authority. Neither Abra nor Research edits the installation template to author an individual report.

Retain `.abracode/reports/generated/<issue-id>/<revision-id>/index.html` with input digest, output digest, execution/generation, source report ID and build status in an optional artifact receipt alongside existing report identity. Keep the Markdown research receipt authoritative for research acceptance; visual output is an attachment. A stable build request determines the revision, and changed inputs require a new revision. Completed retained research can be rendered later through an artifact-only operation that reads immutable workflow evidence without reopening its execution or resurrecting its worker.

Build from an isolated temporary workspace and independent cache/output paths, using immutable installed toolchain/dependency assets. Parameterize the existing Vite/license/diagram paths so copied build inputs do not rely on the current `../..` installation-root assumption. Bound subprocess output/deadlines and global concurrent report builds using a finite local Effect semaphore, separate from worker execution capacity; retain pending intent across restart. Stage the finished artifact on the destination filesystem, validate single-file assets/notices/size and digest, then atomically rename under the existing report lock after ensuring the revision is unoccupied. Never overwrite an existing different artifact. Only then advertise a receipt. Crash after rename is recovered by path/identity/digest reconciliation before rebuilding. Temp cleanup removes only validated owned scratch paths; retained artifacts survive native worktree retirement.

Offline feedback is a local form plus a selectable Markdown/JSON export and optional Blob download. Clipboard/download limitations in native sandbox preview must have the selectable-text fallback. No network, local storage, cookies, service worker, prompt bridge or approval action is required. Preserve all applicable notices and existing explicit loopback preview behavior.

### 11. Complexity and authority check for each new mechanism

| Choice                      | Can OpenCode already do this?                                            | Can AbraCode already do this?                                             | Additional owned state/behavior and fewer moving parts                                               |
| --------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Prompt intents/messages     | Queue, steer, inbox, context, events; not business authorization/answers | Assignment capture, generation guards, questions and uncertainty patterns | One bounded intent/response collection and shared guard projection; no transport or transcript store |
| Batch intake                | Not the issue/dependency authority                                       | Single-item transactional creation and claims                             | One SQLite transaction plus batch receipt in the same graph; no saga/second database                 |
| Fair dispatch               | Native queue owns within-session execution, not project-level policy     | Existing scheduler, readiness, claims and capacity                        | Small tie-break cursor and message-aware reservations; no new scheduler                              |
| Supervision posture/summary | Native outcomes/events/forms                                             | Existing attention, monitor, waits, budgets and read model                | Composition and projections; only notice delivery identity persists, no display lifecycle            |
| Task profiles               | Native model selection/inventory                                         | Default/role resolution and snapshots                                     | Small role selector plus provenance in existing input/snapshot; no model router service              |
| Project leads               | Persistent sessions and configured agents                                | Central Supervisor/session authority                                      | Narrow lead identity/scope and registration revision; same tools/protocol, no new orchestrator homes |
| Reports                     | Native HTML preview, not Abra's artifact build policy                    | Solid single-file template, compiler, immutable research receipts         | Trusted snapshot/build adapter and optional HTML receipt; no hosted UI or external wrapper           |

Keep initial message coordination/contracts cohesive, avoid growing `advancement.ts` with a second message implementation, and consolidate legacy steer submission into that coordinator. Extend shared schema/tool/read-model paths instead of copying validators. Do not remove existing question/wait/scheduler/report routes merely for naming symmetry.

## Risks / Trade-offs

- [Native duplicate-ID or hook timing differs from expectations] → Real pinned-server gate precedes protocol development; preserve uncertainty and stop automatic retry if native evidence cannot prove non-admission. Document observed contracts, not assumed exactly-once model effects.
- [Queued messages race completion, pause or capacity release] → Re-read generation/intent, inspect inbox/context, retain reservations and confirm cancellation/quiescence before transition or another writer.
- [Replies arrive during admission bookkeeping] → Use short coordinated updates and fresh merge checks; never hold the global lock while native prompt hooks call back into the controller.
- [Bounded retained messages fill a long execution] → Refuse additional requests with actionable limit evidence; never truncate outstanding obligations or introduce speculative archival machinery.
- [Lead privilege broadens central wildcard management access] → Separate principal type, deny-by-default endpoint/actions and repository predicates, revision validation and explicit refusal tests.
- [Batch creates valid work but policy changes before execution] → Immutable intake identity plus fresh start-time project registration/policy checks; no intake recommendation bypasses gates.
- [Shared report caches or copied root assumptions undermine isolation] → Independent roots/caches, parameterized trusted license inputs, concurrent-build tests, immutable revision publication and crash-window assertions.
- [Report snapshot includes hostile text or executable authored source] → Controller path accepts bounded data only, safe text/link rendering and trusted templates; executable manual TSX follows normal source authority.
- [Existing delivery/recovery work changes overlapping contracts] → Reconcile current diffs and `complete-work-reliably` before affected implementation; preserve its gates/obligations and rerun native regression rather than assuming artifact completion.
- [Same-user processes can access server/files beyond managed controls] → Preserve the documented trusted-process boundary; do not claim permissions/worktrees isolate malicious same-user execution at OS level.

## Migration Plan

1. Before apply, record the current delivery/recovery baseline without resetting or staging unrelated edits. Reconcile the active change's obligations/visibility contracts and use its implemented behavior, not task-checkbox counts, as the baseline.
2. Ship Milestone 0 and then messaging with additive optional schema-owned record fields. Old records retain captured assignment interpretation; unadmitted legacy prompts with missing captures remain blocked. Never synthesize historical steering authorization or reopen terminal work.
3. Add the next transactional SQLite schema migration for batch receipts and later task-dispatch fields, preserving original single-request inputs and mappings. Reject future schema versions and transactionally test upgrades from current schema 3 and supported earlier fixtures. Do not combine plugin storage writes with SQL as though they formed one transaction.
4. Omitted posture/profiles/leads preserve current behavior; new automatic options are explicit. New lead agent configuration uses the existing owned config/reload procedure and validates inventory before admission. No legacy session is silently adopted as a lead.
5. Add report primitives independently; enable controller builds only after isolated publication/recovery tests. Existing Markdown reports and manual build commands remain usable. Never move/delete historical report paths to migrate.
6. Deliver focused slices in this order: M0 steering → M1 communication → M2 batch/fair dispatch → M3 supervision → M4 profiles → M5 leads. M6 reporter work can be developed independently after scope ownership is fixed; final acceptance combines all slices. Each slice includes architecture/doc updates, refusal/restart evidence and a review for duplicated machinery, authority, races and stale identities before acceptance.
7. Upgrade a running service only through existing controlled stop/config/restart procedures after reconciling uncertain operations. Preserve SQLite/plugin records and retained files. Rollback requires a compatible writer that preserves new intents/receipts; do not run an older writer that drops them, downgrade SQL blindly, replay uncertain operations or delete outputs to make old code appear healthy.

### Verification and evidence plan

Use existing unit/SQLite/runtime fixtures for identity, strict schemas, duplicate/conflicting replies, stale generations, policy precedence, cycle rejection, transactional rollback and classification. Extend real native E2E for authorized/direct steering, busy queue, response loss, queued restart, explicit reply delivery, interrupted outstanding request, forwarded findings, two-slot/three-task dispatch, independent Review/Apply permissions, session/worktree persistence and human plan/exact-head merge gates. Add lead scope/disable/restart/provenance tests only after the communication gate passes.

Extend reporter browser tests for manual/data-driven examples, invalid diagrams, hostile inert evidence, source provenance/time labels, keyboard/narrow layout, offline relocation/sandbox preview, multiple isolated builds, failed publication and digest recovery. Existing automated sandboxed-browser tests prove artifact behavior; inspect the pinned graphical client's actual HTML link/preview behavior for handoff and retain its observed result separately rather than claiming a browser emulation proves the client UI.

At each milestone run relevant focused checks, then `pnpm check`, `pnpm test`, `pnpm test:e2e` as required by the repository.
