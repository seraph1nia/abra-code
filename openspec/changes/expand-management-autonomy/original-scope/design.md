# Design

## Context

See [proposal.md](proposal.md) for motivation and [audit.md](audit.md) for observed behavior, measurements and newly executed baseline checks. Planning targets checkout `d38274bb72697a92cd0fdd52bab4cd065a3688dd` on 2026-10-18. The proposal extends the existing flat capability paths; it does not replace the recent messaging/scheduling/lead/report work.

## Goals / Non-Goals

**Goals:** Extend established state owners with finite response recovery; make resolved history cheap; prove fault/restart behavior; expose authoritative fleet/communication information; delegate routine intake with transactional limits. Keep each work package independently reviewable and verifiable.

**Non-Goals:** A new orchestration service, scheduler, queue, database, cache authority, UI framework, management hierarchy, agent harness or watcher. No terminal adapters, message files, Firstmate homes or remote-host layer. No Lavish integration. No reporter rewrite. No automatic tool installation or live-provider access. No declaration that deterministic success establishes autonomous task judgment or Firstmate parity.

## Decisions

### 1. Deliver P0 → P1 → P2 as gated increments

Keep one coherent OpenSpec change because the cross-cutting contracts and final scenario belong together, but use the twelve work packages below as implementation/review units. Existing behavior gets evidence or a regression test, not redundant new code. P0.1–P0.4 correctness, finite-turn and cleanup gates must pass before any grant-enabled native scenario or P2 production authority is enabled. P1 depends on the P0 communication contract; P2 uses the P1 visibility for inspection. P2.3 audit findings can reduce P0/P1 code locally, but never justify an unrelated rewrite.

| Package                | Existing owner / proposed increment                                                          | New retained state                                                                        | Native dependency                                                                        | Risk / acceptance evidence                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| P0.1 messaging audit   | Messages, Sessions, Runtime, Guards; transition and outcome matrix, fix only reproduced gaps | None unless a demonstrated crash window needs provenance                                  | Exact inbox/message/history and native outcome ordering                                  | High authority risk; forged prompts, lost responses, cancellation, duplicate/out-of-order events and generation regressions |
| P0.2 response recovery | Messages owns reminder, Sessions triggers after verified idle, Attention owns incident       | Optional one-attempt metadata on original request; existing incident/budget fields reused | Exact consumed input + relevant subsequent native turn, same guard/preflight/prompt path | High duplicate/loop risk; full required-response matrix and restart/race evidence                                           |
| P0.3 performance       | Messages candidate selection, tick-scoped Runtime observation reuse                          | None                                                                                      | Existing reads, bounded exact/history fallback                                           | Medium false-idle risk; equivalent baseline/after workloads, independent session observation and cancellation checks        |
| P0.4 operations        | Existing test harness, fixtures and observability                                            | Test evidence only                                                                        | Isolated native service/loopback provider/forge and native cleanup APIs                  | Medium fixture complexity; repeated lifecycle, fault/restart/idle/report postconditions and retained metrics                |
| P1.1 fleet             | Visibility snapshot/classifier/home                                                          | None                                                                                      | Existing synchronized native activity                                                    | Medium inaccurate totals; pagination, filters, unknown state and native TUI assertions                                      |
| P1.2 communication     | Visibility detail/client/protocol; paginated query reuse                                     | None                                                                                      | Read-only message/session/report/form observations                                       | Medium hidden obligations; page boundaries, timestamps, recovery state and permission probes                                |
| P1.3 quiet supervision | Attention + existing monitor/lead notices                                                    | Existing incidents extended with digest membership only if necessary                      | Existing native prompt/notify routes                                                     | Medium loss/noise risk; source identities, late arrivals, restart and posture/budget counts                                 |

This avoids a giant implementation patch. Every increment records actual checks and limits before the next begins; `tasks.md` encodes the gates.

### 2. Keep transport disposition and response obligation distinct

The original request remains the business identity. No new top-level message disposition is needed. Admission is a native fact; acknowledgement/answer are authenticated worker commits. Recovery and notification are orthogonal to both.

| Disposition                | Owner / entry evidence                                                 | Valid forward transitions                                                                                | Reconciliation / restart and authorization                                                                                                              |
| -------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending`                  | Controller exact intent committed, submission not begun                | `admission_uncertain`; authorized cancellation/supersession                                              | Validate current assignment/role/generation/location, capacity and preflight before submission; retain identity on refusal                              |
| `admission_uncertain`      | Controller persisted intent before native call; receipt missing        | `admitted`, explicit ack/answer when exact authorized invocation proves response; authorized disposition | Query original ID. Absence/error cannot authorize a new ID or prove non-admission. Persist ambiguity                                                    |
| `admitted`                 | Exact native payload established in inbox or retained message          | `acknowledged`, `answered`; authorized cancellation/supersession                                         | Queued vs consumed remains a native observation. Eligible verified queue wake reuses the same ID and payload, never a replacement instruction           |
| `acknowledged`             | Expected current worker explicitly commits original request/generation | `answered`; authorized disposition when still unresolved                                                 | Terminal for acknowledgement-only; active for answer-required. Admission or execution success alone cannot establish it                                 |
| `answered`                 | Expected current worker commits correlated bounded reply/evidence      | Historical retention; explicit history-preserving control disposition only where needed                  | Terminal for response; accepted reply survives assignment/generation changes. Never reinterpret later native outcomes as invalidating it                |
| `cancelled` / `superseded` | Explicit controller control transition                                 | No revival                                                                                               | Reconcile owned queue/consumption under existing stop semantics. Preserve evidence and any accepted response; do not claim consumed effects were undone |

Default/legacy `response: none` means no response obligation. It does not by itself prove transport was consumed: an admitted no-response instruction can still be queued and need wake/cancellation reconciliation. Filtering must use actual transport/ownership requirements, not merely `requiresResponse === false`.

New reply submission still requires current ownership; historical reading never does a new worker admission check. `messageHistoryError` currently treats non-status/reply fields as immutable identity: optional recovery metadata must be separated explicitly and validated with its own monotonic rules. Preserve old record decoding, identities, timestamps and reply content. Do not put mutable recovery fields into the immutable identity comparison by accident.

P0.1 also tests the pinned replay limitation documented in `docs/supported-apis.md`: native duplicate-ID reconciliation precedes the plugin hook and returns the original payload. The controller refuses conflicting content; it must not promise that the hook can reject every native duplicate request. No changed instruction is thereby authorized.

### 3. Put the one reminder on the original request

**Chosen representation:** optional `response_recovery` on the shared retained request contract, with a single attempt slot: exact reminder prompt ID/text, preparation time, monotonic transport disposition (`pending` → `admission_uncertain` → `admitted`, or explicit suppression), and compact verified consumed/turn observation identity/time. Keep an optional terminal reason only when it cannot be reconstructed from an existing incident/control transition. There is no attempts array, separate request history, reply-recovery store or second work item. The existence of the slot reserves the sole automatic attempt; restart cannot reset it.

The parent request already supplies request ID, session/generation, role/assignment (for workers) and registered revision (for leads). Do not copy those into another authority record. Response resolution derives from original acknowledgement/reply; escalation resolves through the existing Attention incident/disposition. The exact schema field names can follow local naming conventions, but reviewers must count the actual fields added and validate monotonic transitions.

Alternatives rejected: a second ordinary business request creates two apparent obligations; a watcher duplicates the existing monitor; inference from `capacity_observed_idle` alone has no proof that the particular input was consumed before completion; a generic retry engine obscures the one-attempt rule.

**Admission procedure:**

1. Under the existing execution/lead operation ownership, select current unresolved required responses. Read native session and exact prompt evidence. Preserve failure/interruption and unknown ownership classifications from the runtime adapter.
2. Require consumed original input plus a positively observed successful native idle turn after that consumption. No original or relevant recovery prompt may remain queued and no relevant turn may still execute. If retained context cannot prove ordering after compaction, use bounded exact/history lookup; if it still cannot, retain uncertainty and surface a blocker. A session-level success marker is insufficient.
3. In a short fresh commit, revalidate parent response, current assignment/session/generation/role/location or lead registration, pause/disable/revocation, captured policy/posture and finite budget. Reserve at most one reminder identity and the existing appropriate capacity. Charge one diagnostic turn at first reservation, not per tick; no budget reset or refund that permits a new ID after uncertain admission. Default diagnostic budgets already zero disable this behavior conservatively.
4. Validate the exact nested reminder intent through the normal native prompt guard and preflight. Persist `admission_uncertain` before native submission. The reminder asks only for `abra_worker_reply`/lead reply to the original request, with the missing acknowledgement or answer. No new substantive work, scope, checkpoint approval or background loop is granted.
5. Reconcile lost receipts by exact reminder ID. Only a verified eligible queued prompt can be woken with the same ID and payload under the existing wake semantics. An absent uncertain prompt is never silently resubmitted or replaced.
6. Re-read after response/admission effects; merge into current state so a reply committed during the native call cannot be overwritten. If the original response was already accepted before admission, suppress the unused reminder. A newly started unrelated authorized turn causes waiting and fresh observation rather than a second queue instruction.
7. A successful correlated response resolves the original requirement. A completed reminder without response, failed/interrupted reminder, exhausted budget or unavailable/unsafe state produces or updates **one** stable `message_pending` incident keyed by original request and generation. Reason is explicit; uncertain evidence never becomes an accusation. Escalation has no new automatic retry allowance.

An escalated obligation continues blocking checkpoint advancement until an authorized response or explicit control disposition. Displaying/handling the incident is not equivalent to answering the request. Explicit user resume/retry stays the existing control action and must explicitly supersede the old obligation if moving generations. Manual mode adds no automatic reminder. Attended automatic/unattended can use one within captured diagnostics and capacity; human forms and approval ownership never change.

Use the same contract for lead requests before increasing lead autonomy. Lead wakeups consume management capacity and source-issue diagnostic budget through existing `leadAccounting`, not an additional free budget. A failed/revoked lead cannot be used as a recovery recipient. Keep shared transport/transition helpers small; worker and management authorization remain distinct callers.

### 4. Optimize active work using evidence, with session observation independent

The planning probe establishes redundant adapter reads; it does not measure native latency, locks, scheduler delay or memory. P0.3 first makes the probe reproducible in the test tooling and captures those additional metrics at the appropriate layer before editing the hot path.

Build one per-tick index of relevant request IDs/native prompt IDs. Exclude answered and acknowledgement-resolved history from recurring transport reads unless cancellation/ownership/checkpoint recovery needs an exact ID. Keep unresolved answers, uncertain/pending submissions and unresolved queue wake/cancellation active. Preserve the original immutable records for conflict checks and history. Avoid `messageRequests(e.messages).some(...)` inside each candidate's native outcome classification: build the current-assignment prompt set once.

One request-scoped observation bundle can supply session, inbox and context snapshots to relevant lookups. Exact-message lookup remains bounded for IDs absent from compacted context. Do not repeatedly fetch full context/inbox once per ID when a single snapshot establishes the same facts. Invalidate/re-read the bundle after a native mutation or changed durable ownership; it is never an admission authority. Always observe assignment execution independently even when active message candidates are empty.

Target: zero recurring native message-admission reads for 200 resolved records; bounded session/inbox/context reads and O(active requests) exact lookups for a fixed unresolved set. Storage decode/serialization may remain O(retained records); measure that separately and do not promise constant total runtime. No O(N²) classification or unbounded history scan. Leave unrelated code alone when profiling shows negligible impact.

### 5. Build operational proof in the disposable harness

Reuse `tests/e2e/install.ts`, existing deterministic provider/recording forge, native client, isolated config/data/cache/state, local repositories and bare remotes. The current native test is already large: extract a focused fixture seam only where needed to run repeated journeys without duplicating its service lifecycle. The opt-in runner has explicit seed, cycle count, concurrency, deadline and fault schedule; it is a bounded command, not a daemon or new polling framework.

Use three proof layers:

- Unit/SQLite tests enumerate state transitions, authorization refusals, repeated ticks and concurrent commits deterministically.
- Opt-in native soak repeats parallel/message-heavy/failure-heavy/idle/restart journeys and verifies outputs and cleanup. Exercise provider errors, omitted response, lost receipts/events, interruption, unavailable state, project-lead notification, report publication and delivery/retirement windows. P0 can run current proposal-only lead scenarios; grant scenarios are added after the gate.
- Real-provider recipe is separate, requires explicit operator authorization plus credentials, uses disposable representative tasks, and never runs in ordinary CI. Planning and future deterministic apply work do not authorize it.

Emit versioned JSON plus bounded logs and applicable portable reports to a fresh evidence directory outside the removed installation. Include seed/revisions/versions, executed/skipped scenarios and assertions, task/intervention counts, provider requests vs native turns vs tool calls, recoveries/duplicates/unanswered requests, scheduler wait, decision wait and notification latency, reconciliation mean/max, lock occupancy, CPU/RSS samples, retained state bytes and residual processes/worktrees/queued prompts/report builds. Unknown usage remains unknown; trustworthy attributable provider token reports are optional. No prompt bodies, raw provider responses, secrets or credentials in telemetry by default. A failed cleanup is a failed postcondition, not a pass with an invisible footnote.

Acceptance includes the backend-maintenance scenario from the request using disposable sample tasks. Deterministic execution proves controller/runtime behavior; record that it does not establish natural-language decomposition or actual authentication-refactor quality. Real-provider task quality is assessed only when run. Multi-cycle duration and resource baselines must be recorded; one fixture run is not a soak claim.

### 6. Use the native read model for a fleet control surface

Extend `visibility/protocol.ts` and `read-model.ts` from existing `supervisionAggregate`, readiness blockers, native activity, decisions, attention, lead records and message queries. Do not persist fleet counts. Home adds fleet totals/per-repository rows and attention shortcuts; detail adds compact communication rows and expandable bodies/evidence with lazy pagination. Add a lead list/detail path using the same native navigation and theme.

Keep mutually exclusive primary task classes separate from nonexclusive attention counts. Show native queued and ready/capacity-wait states separately; retain dependency, supervisor, human, recovery and delivery reasons in details. For completed-today derive actual graph closure/completion timestamps (existing work events or execution completion history) using the host's local calendar day with an explicit boundary. Do not count the current closed page as total; an unavailable/truncated aggregate says so. A read-only indexed aggregate query over existing events is preferable to scanning full history once per task or adding a fleet table.

Lead summaries show scope, enabled/stopped/recovery state, session availability, outstanding requests/proposals, latest meaningful outcome and, in P2, grant status/usage. Messages show native admission separately from explicit acknowledgement/answer, original request identity, sender/recipient/kind/time, bounded body/reply and recovery attempt/native observation/escalation. Worker questions link to the existing Decision record with owner, role, actual question, impact and clearing action. Nothing resolves a question by reading it.

Use existing native worker inspection and report/PR navigation. Retired evidence is labeled unavailable, generated HTML uses the Vite/Solid reporter/host preview, and conversation actions return to Abra. Any optional management button invokes existing authenticated controller routes/native forms; observer RPCs remain read-only. Test disconnect freshness, pagination, invalid records, keyboard focus/remapping and absence of a worker composer.

### 7. Coalesce meaningful outcomes without duplicating notification ownership

The monitor already coalesces events and periodically reconciles. Attention currently batches communication references within one execution, suppresses repeated references and reserves finite diagnostic capacity; it does not provide a cross-task outcome digest. Add a pure classification helper near Attention for silent, digest-worthy and immediate-attention observations. Reuse incident IDs/dispositions as source truth.

Build a bounded deterministic digest over pending existing incidents in a supervision cycle. Elect one existing source incident as the batch anchor; retain the exact source incident IDs on that anchor before admitting one native prompt. Other sources are marked covered only by that retained membership, never handled implicitly. A lost admission receipt retries/observes the anchor prompt ID. Late incidents remain for the next digest. Budget charge is recorded against an identified source before admission, with no new free supervisory budget or duplicate per-source wakeups. If reliable cross-record reservation cannot be expressed with current short coordination commits, introduce only minimal membership on existing incidents and a conservative anchor-first commit protocol; partial reservation is reconciled from the anchor, not a new notification store.

Immediate items keep direct visibility and the existing native human forms independently of the digest slot. Unattended suppresses user-only explanatory wakeups while retaining decisions; returning to attended mode surfaces unresolved important sources once. Manual does not admit automatic routine reasoning. Tests count actual prompt IDs/turns: unchanged polls yield zero, related routine outcomes share one, and no unresolved decision disappears through digest disposition or exhausted budget.

### 8. Put grant authority and intake accounting in the existing SQLite transaction

Current leads persist proposal/notification state through plugin storage, which has no public transaction/CAS. The SQLite graph already atomically creates batches/items/dependencies. Counting budget in the lead record followed by a separate SQL commit would create crash windows and concurrent overspending.

**Chosen extension:** a versioned grant relation in the existing work database, plus a nullable immutable grant/version/lead-registration binding on existing batches. Derive total used tasks through existing `batch_items` joined to the bound batch; do not create a second task store, usage counter ledger or separate database. Index grant-bound batch and item-to-issue lookup paths. A grant row stores schema/version identity, lead ID/registration revision, repositories, allowed task kinds/workflows, maximum new/active tasks, required expiry, scheduling permission and revoked state/time. Grant scopes intersect current registered scope/project policy; no client field can enlarge them. Task kind is a narrow admitted category (investigation or minor correction) validated with the corresponding workflow and retained batch provenance, not a general policy engine.

Only Abra's existing authenticated control path issues/revokes grants. No implicit grants on upgrade; a lead never grants or revises itself. Grant issuance defaults to existing human approval requirements and cannot relax them. A grant binds one registration revision; scope/model/session revisions require an explicit new grant. New total allowance requires explicit new authority, not an automatic budget reset.

**Intake:** validate native caller/current registration in a short coordination section, normalize using WorkIntake, then inside one SQL transaction revalidate active grant/version/expiry, project-policy snapshot, repository/dependency/task-kind/workflow restrictions and remaining total budget. Insert ordinary batch/items/dependencies with the grant binding. Existing request identity returns the original mapping and derived usage after response loss; conflicting content or grant binding fails. An unauthorized lead cannot use a retry to admit work, but Abra can inspect a committed historical receipt after revocation. Keep parent supervisor identity on executions: lead provenance is not worker ownership.

**Scheduling:** `allow_scheduling` permits a request to the existing central scheduler, never a new scheduler or override of global auto-scheduling policy. Define a grant-active task conservatively as a grant-created issue with an existing controller claim and not yet closed/released; paused/approval-waiting tasks count. Check the grant active limit in the same SQLite claim transaction, together with existing unique ownership; existing global/repository/role/retained-resource capacity remains enforced by the controller. This is separate from native compute occupancy. A task admitted but not claimed consumes total budget, not an active slot. Releasing compute alone never frees the grant's active-task slot.

Revocation/expiry denies new **delegated** mutations and automatic grant-based claims. Queued tasks remain ordinary recorded work, visibly awaiting authority; Abra may explicitly start preserved authorized work through its ordinary controller route, retaining provenance and applicable capacity/approval rules. Running work continues under its captured controller authorization. Existing human decisions/Review/merge/retirement gates remain unchanged. Do not automatically cancel/delete already authorized tasks when future lead authority is revoked.

**Cross-store order:** lead disable/scope change first revokes the relevant SQLite grant under controller coordination, then saves the revised plugin registration, then reconciles native stop/queued requests outside coordination. A crash between revocation and registration save fails closed. Grant issuance validates current plugin registration while coordination is held before a synchronous SQL commit. No native API or awaited provider call occurs inside that section. This keeps one authorization order without pretending plugin storage and SQLite form one database transaction.

Alternatives rejected: prompt-only limits are unenforced; plugin counters plus SQL tasks are not atomic; a new usage store duplicates task provenance; grant scheduling directly spawning workers bypasses central admission. Extend current intake/claim contracts, avoiding a generic authorization subsystem.

### 9. Treat revocation and historical work separately

Test idle/active lead, pending proposal, committed delegated batch, queued message, running task and pending human approval at disable/revocation/expiry/scope revision. The transition revokes future control first; native interrupt/cancel confirms only actual queue/stop results. Consumed instructions stay historical and cannot mutate through a revoked native principal. Already committed tasks/proposals/replies remain inspectable, with explicit historical or superseded status.

Lost registration response, idempotent session creation, interruption/model unavailability, answered-before-notified, parent Abra restart and commit-before-receipt all reconcile via existing retained IDs/locks. Preserve retired-session recognition so stale leads cannot masquerade as Abra. Lead prompts/recovery share explicit management capacity and diagnostic budgets; no lead registration by another lead and no recursive wakeup chain. A notification is evidence delivery, never intake authority.

### 10. Simplify only demonstrated overlapping responsibilities

Complete an ownership ledger for Leads, Messages, Attention, Runtime, Advancement and VisualReports: persisted writes, native effects, lock ordering, idempotence, permission checks and crash windows. Trace lock order from controller coordination to per-execution/per-lead/attention/report operations; avoid acquiring an outer operation lock while holding coordination. Await native calls/report builds outside global coordination. Target concurrent message/lead changes, long report builds alongside scheduler admission, stale result commits and interrupted reservations.

Extract small pure helpers only for actually shared semantics (candidate selection, correlation equality, grant evaluation/accounting, notification classification, compatibility). Keep service-owned persistence/native effects in the service; no generic rules engine or LOC-driven service split.

Inspect existing hard bounds before extending them: 256 execution communications, 128 lead requests, 32 proposals, 32 retired lead sessions, and current attention/report/round limits. The current code refuses new entries rather than evicting history; preserve unresolved records. Pagination does not make retained arrays unlimited. If soak evidence shows these caps impede sustained operation, add targeted resolved-history pagination/archival within existing stores and prove immutable identity/receipt lookup; never silently truncate unresolved authority or increase limits without measurement.

Measure production LOC, changed files, persistent schema fields/relations, native reads, processes, dependencies and behavioral test coverage before/after. Explain responsibility/crash-path improvements; LOC alone is not maintainability proof.

## Risks / Trade-offs

- Native consumed/turn causality may be unavailable after compaction or adjacent contradictory idle markers → bounded exact/history fallback and durable uncertainty/escalation, never speculative recovery. Availability is traded for identity safety.
- Reminder preparation races a reply, pause or scope revision → fresh commit/admission guard checks and merge into current records; one durable attempt slot survives restart.
- A reminder uses model/capacity budget → charge existing captured finite diagnostics and ordinary execution/management capacity; zero budget/manual mode stays quiet and actionable.
- Cross-task digest partial commits could double-deliver or hide incidents → one retained anchor/membership protocol, stable prompt ID and source dispositions unchanged until explicit handling.
- Grants cross existing plugin registration and SQLite graph storage → fail-closed revoke-first ordering, one short controller coordination boundary and atomic task/grant accounting; actual SQLite crash/concurrency tests.
- Conservative active-task caps can keep another lead task waiting on approval → show the specific grant limit separately from compute capacity; preserve user-selected bounded autonomy.
- Soak fixtures may become another orchestration system → reuse existing lifecycle/provider seams; bounded CLI, no production loop or daemon.
- UI counters can overstate coverage or freshness → counts from authoritative aggregate/event evidence, explicit day/coverage/truncation labels and unknown states.
- Historical caps may limit very long service lifetimes → record actual pressure and preserve unresolved records; change retention only with proven need and replay safety.
- Baseline test-worker SIGSEGV is unresolved environmental/runtime evidence → retain failed result and isolate rerun; do not weaken tests or attribute cause without reproduction.

## Migration Plan

1. Land P0 schema compatibility/transition tests and optional recovery fields before enabling any reminder. Existing missing metadata means unattempted, not pre-authorized. Current zero diagnostic defaults and manual posture remain conservative. Keep exact historical identities readable.
2. Land active-candidate/observation changes with equivalent before/after evidence and full cancellation/restart regressions. Add opt-in soak tooling; no automatic provider or browser provisioning.
3. Land native read-model/UI and quiet-supervision increments with versioned protocol decoding and existing invalidations. Update docs as implemented behavior becomes available.
4. After the P0 gate, migrate the existing work database forward for grants and nullable batch authority binding. No grants are seeded. Preserve ordinary batch results and captured execution policies. Test fresh and upgraded databases, rejected newer versions, response loss and concurrent grant claims.
5. Implement grant control/actions and native proof behind absence-of-grant deny-first behavior. Revoke/expire before accepting changed registration authority. Complete combined scenario and the full commands in `tasks.md` before describing the cycle as operationally accepted.
6. Rollback: stop only the owned installation through the documented operator procedure, disable automatic behavior/revoke grants through current controls, and preserve all existing tasks/receipts. A code downgrade must use an expressly supported schema path or restore a consistent backup of the work graph plus plugin/native retained state; never delete new grant/response evidence to force an old binary to run. Already admitted native work remains subject to explicit reconciliation rather than replay under fresh IDs.
