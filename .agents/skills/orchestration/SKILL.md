---
name: orchestration
description: Turn requested goals into work graph issues, start OpenSpec exploration, manage registered work, and explain execution blockers through the Supervisor tools.
---

Use this workflow in the central Abra conversation (logical Supervisor). Abra is the only user conversation. Worker selections are read-only inspection; route questions and instructions through Abra. When the user asks for new work or a new OpenSpec flow, identify the registered repository from conversation context or `abra_project_list`, check `abra_work_list` for an existing matching issue, and use `abra_work_create` if the work is new. Supply `repository_id`, a short `title`, and the requested goal as `description`; optional `priority` is 0–4 (default 2) and `dependencies` contains existing issue IDs. Use a stable `request_id` for this request and reuse it with the same input on retries; choose a new key for intentionally separate requests. Creation returns the issue and readiness and does not itself launch workers.

If the user asked to start, call `abra_work_start` with the returned `issue.id` when eligible. Do not ask the user to create an issue elsewhere. Explore inspects existing code and turns the goal into a proposal; uncertainty about implementation details belongs in that proposal and its human plan approval. Clarify only when the requested goal or repository cannot be chosen from context. `abra_work_ready` returns dependency, setup, policy and capacity blockers. `abra_work_start` creates or recovers the execution. One issue owns one worktree throughout Explore, Apply and Review.

Inspect progress through `abra_work_status`; use `abra_work_control` for `steer`, `pause`, `interrupt`, `resume`, `retry` or `advance`. Do not infer completion from conversation text. `abra_work_approve` takes `issue_id` and `kind` (`plan` or `merge`) and creates a native approval form. Only an answered human form authorizes the checkpoint. A pending form is a stopping condition for the dependent phase.

`abra_work_finish` verifies delivery and safe cleanup before issue closure. Failures retain resources. Read [operations](../../../docs/operations.md) for setup and [recovery](../recovery/SKILL.md) for ambiguous operations.

Inspect retained `decisions` and `waits` in `abra_work_status` independently of the latest progress. `abra_work_decision` takes `issue_id`, `key`, `generation` and `action`: `answer` requires a Supervisor-owned decision plus `answer`; `collect` creates/recreates a user-owned native form or collects its answer; `cancel`/`supersede` retain an explicit disposition. User answers never substitute for plan/merge forms. Expired/invalid waits require inspection; `abra_work_wait_disposition` explicitly supersedes one with matching generation and a concrete `evidence` reason. Never clear ownership records to silence a wait.

Select `workflow_policy` explicitly for research-only or lightweight-fix and include `scope: {goal, acceptance, constraints}`. Full OpenSpec remains the default. Research yields a retained report through abra_work_report and never delivers code. Lightweight uses scope approval, checks, independent Review and delivery without OpenSpec artifacts. Incomplete scopes create a user decision before launch; collect it or explicitly revise with abra_work_scope. A research follow-on is a new implementation issue/request, with its exact report_reference and dependency; never convert the research issue or auto-start a recommendation.

AbraCode tool successes expose `{ok:true,result?:...}` as native structured output and matching JSON content. Rejected actions are native failed tools, with a safe code and recovery guidance; do not expect an `ok:false` success envelope. Routine classified waits remain successful data. Progress notifications are ephemeral observations, never checkpoint authorization. Inventory failures preserve the retained admission intent: inspect configured agent/model/variant at the worker location and repair it before an explicit retry; do not choose a substitute provider automatically.

Repository intent lives in the selected ignored `abracode.yaml`. `abra_config` with `action: status` distinguishes pending, applied, failed and retained/undeclared declarations; `action: apply` explicitly reconciles manual edits. The operator can use `pnpm config:apply` without a model turn while Abra is idle. Startup and static validation never register entries. Omission blocks new work without removing retained resources. See [onboarding](../project-onboarding/SKILL.md) for saved-versus-applied recovery.

Model defaults and complete role overrides come from personal configuration, with logical `supervisor` mapped to Abra. An execution captures its model/profile selections and repository policy. Session-local UI choices and later config edits do not change retained work. Inspect captured/configured/native model evidence before recovery; unavailable models or variants require repair and an explicit retry, never an automatic substitute.
